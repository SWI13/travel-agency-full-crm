# Database

The data model is defined once, in `app/server/store/schema.ts`. That file drives table creation in Appwrite, field whitelisting, and the unique constraints of the local demo datastore.

## Setting up Appwrite

1. Create a project in Appwrite Cloud or on your own Appwrite server.
2. *Overview → Integrations → API keys → Create API key* with these scopes: `databases.read`, `databases.write`, `tables.read`, `tables.write`, `columns.read`, `columns.write`, `indexes.read`, `indexes.write`, `rows.read`, `rows.write`, `users.read`, `users.write`, `sessions.write`. (Scope names follow your Appwrite version; grant the database, table/column/index/row and user scopes.)
3. Put the endpoint, project ID and key in `.env` (`APPWRITE_ENDPOINT`, `APPWRITE_PROJECT_ID`, `APPWRITE_API_KEY`). Optionally change `APPWRITE_DATABASE_ID` (default `umrah_crm`).
4. Start the app. On first use it creates the database, the 12 tables, their columns and indexes. This is idempotent: later starts only add what is missing. The first start can take a minute while Appwrite builds the columns.
5. Open *Integrations* in the dashboard: the **Database** line turns green after a write / read / update / delete round trip succeeds. If it is red, the exact Appwrite error is shown under it.

Tables are created **without client permissions and without row security**: they are reachable only with the server API key. The browser never connects to Appwrite. Employees are Appwrite Auth users; their profile and role live in the `staff` table.

Recommended in the Appwrite console: restrict the API key to these scopes only, and keep the email/password auth method enabled (the server uses it to verify passwords).

> This driver targets the TablesDB API of `node-appwrite` 31 and is verified against self-hosted **Appwrite 2.7.2** (109/109 end-to-end checks, see `docs/TESTING_REPORT.md`). Run `npm run test:appwrite` after connecting a new project: it uses a temporary database and removes it afterwards.

## Local Appwrite with Docker

`infra/appwrite` holds a self-hosted Appwrite generated by the official installer (git-ignored: it contains local secrets). It was created with:

```bash
docker run --rm -v //var/run/docker.sock:/var/run/docker.sock \
  -v "<project>/infra/appwrite:/usr/src/code/appwrite:rw" \
  --entrypoint=install appwrite/appwrite:2.7.2 \
  --http-port=127.0.0.1:8080 --https-port=127.0.0.1:8443 --interactive=N --no-start=true
cd infra/appwrite && docker compose up -d      # first start downloads ~9 GB of images
```

Then `npm run appwrite:bootstrap` creates the console account, the project `umrah-crm-local` and a server key, and writes `infra/appwrite/app.env`. Use `npm run dev:appwrite` / `npm run test:appwrite`; `npm run appwrite:stop` frees the ~3 GB of RAM.

Driver notes learnt on real Appwrite: rows are always created with every column (Appwrite rejects empty data); dates come back as `+00:00` and are normalised to `Z`; boolean columns marked `nullable` keep null.

## Tables

`id`, `createdAt`, `updatedAt` exist on every record (Appwrite's `$id`, `$createdAt`, `$updatedAt`).

| Table | Purpose | Key fields | Indexes |
|---|---|---|---|
| `staff` | Employee profile (id = auth user id) | name, email, role (`admin`/`manager`/`agent`), isActive, lastLoginAt | email (unique), role |
| `leads` | One per customer contact | phone (E.164), waUserId, waName, displayName, serviceType, stage, priority, assignedTo, source + ad fields (adId, adTitle, adBody, adSourceUrl, ctwaClid), refCode, utm, first/last message, lastInboundAt, lastOutboundAt, firstResponseAt, lastActivityAt, unreadCount, travel interest (packageId, departureCity, dates, adults, children, roomPreference, budgetDzd), nextFollowUpAt, notes, tags, lostReason, isDemo | phone (unique), waUserId, assignedTo, stage, lastActivityAt |
| `messages` | Conversation record | leadId, waMessageId, direction, type, body, timestamp, status, referral (raw ad data), isHistory, processed, isDemo | waMessageId (unique), leadId, timestamp |
| `packages` | Umrah / Hajj offers | name, nameAr, slug, refCode, category, descriptions, durationDays, departureCity, flightInfo, makkahHotel, madinahHotel, hotelCategory, transport, roomOptions, priceDzd, defaultCapacity, status, coverImage, isDemo | slug (unique), refCode (unique), status |
| `departures` | Dated groups of a package | packageId, groupName, departDate, returnDate, departureCity, capacity, priceDzd (overrides package), status, flightInfo, notes | packageId, departDate |
| `bookings` | Confirmed sale | leadId, packageId, departureId, customerName, travelers, totalDzd, paidDzd, paymentStatus, bookingDate, assignedTo, notes | leadId, departureId, assignedTo |
| `pilgrims` | One per traveller of a booking | bookingId, leadId, departureId, fullName, checklist (completion flags), visaStatus, assignedTo | bookingId, departureId, assignedTo |
| `followups` | Scheduled tasks | leadId, dueAt, assignedTo, reason, notes, status, completedAt, completedBy, createdBy | leadId, assignedTo, status, dueAt |
| `activity` | Audit trail (append-only) | actorId, actorName, actorType, action, entityType, entityId, leadId, description, meta, visibleTo | leadId, action, actorId |
| `settings` | Single record `agency` | agency profile, crmLocale, soundDefault, autoAssign, autoContacted, checklistItems | – |
| `integration` | Single record `whatsapp` | webhookVerifiedAt, lastWebhookAt, lastRealEventAt, lastDemoEventAt, lastError, lastTest* | – |
| `webhook_events` | Raw webhook deliveries | status, error, summary, payload, isDemo | status |

## Relationships

```
staff 1 ── n leads (assignedTo)          packages 1 ── n departures
leads 1 ── n messages                    departures 1 ── n bookings
leads 1 ── n followups                   bookings 1 ── n pilgrims
leads 1 ── n bookings   (a customer may book several departures)
leads n ── 1 packages   (preferred package)
```

Relations are stored as ids and resolved by the server. Remaining seats are always computed: `capacity − travellers of bookings that are not refunded or cancelled`.

## Integrity rules that live in the design

- **No duplicate leads.** A lead's id is derived from the sender (`sha256` of the phone number, or of the WhatsApp user ID when Meta withholds the number), and `phone` has a unique index. Two webhooks for the same customer always target the same row.
- **No duplicate messages.** A message's id is derived from its WhatsApp message id, with a unique index on `waMessageId`.
- **Idempotent webhooks.** `webhook_events` uses the hash of the raw body as id; a repeated delivery is recognised and acknowledged without reprocessing.
- **Audit trail.** `activity` rows are created by the server only. No endpoint updates or deletes them.
- **Demo isolation.** Every sample or simulated record has `isDemo = true` and can be removed in bulk without touching real records.

## Local demo datastore

When the Appwrite variables are empty, records are kept in `.data/db.json` (git-ignored) with the same contract, including unique constraints and atomic id-based inserts. It is meant for demonstration and development on a single machine — connect Appwrite for real use. To start over, stop the app and delete the `.data` folder.

## Moving from the demo datastore to Appwrite

The two stores are independent: configuring Appwrite starts with an empty database. Re-create the administrator, enter the agency settings and packages again (demo records should not be migrated).
